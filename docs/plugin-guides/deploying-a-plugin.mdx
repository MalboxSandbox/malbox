## Prerequisites

- The plugin executable (PE (Windows), ELF (Linux))
- The plugin's `plugin.toml` manifest

## Configuring a plugin

Every plugin carries its runtime settings in its `plugin.toml`. The SDK bakes
these values into the plugin binary at **build time** - they are **not** read
from the environment at launch. Changing any setting means editing
`plugin.toml` and rebuilding the plugin.

```toml
[plugin]
name    = "my-plugin"
version = "0.1.0"
type    = "guest"

[runtime]
state      = "ephemeral"
execution  = "exclusive"
port       = 50100                       # gRPC listen port
log_filter = "info"                      # tracing EnvFilter directive

[runtime.paths]
sample_dir   = "C:\\malbox\\samples"     # where daemon pushes the sample
artifact_dir = "C:\\malbox\\artifacts"   # where plugin writes output
stash_dir    = "C:\\malbox\\stash"       # internal result stash spillover
log_dir      = "C:\\malbox\\logs"        # log overflow files

[runtime.stash]
threshold_bytes = 1048576                # result stash spill threshold
ttl_secs        = 120                    # stash entry TTL (seconds)
```

All fields in `[runtime]` are optional. When a field is omitted the SDK uses
the following defaults:

| Field | Default |
|---|---|
| `port` | `50051` |
| `log_filter` | `"info"` |
| `sample_dir` | `/tmp/malbox/samples` (unix), `C:\malbox\samples` (windows) |
| `artifact_dir` | `/tmp/malbox/artifacts` (unix), `C:\malbox\artifacts` (windows) |
| `stash_dir` | `/tmp/malbox/stash` (unix), `C:\malbox\stash` (windows) |
| `log_dir` | `/tmp/malbox/logs` (unix), `C:\malbox\logs` (windows) |
| `threshold_bytes` | `1048576` |
| `ttl_secs` | `120` |

## Rust plugins

Use the `#[malbox::guest_plugin]` (or `#[malbox::host_plugin]`) attribute on
your plugin struct. The proc-macro reads `plugin.toml` at compile time and
bakes the resolved `[runtime]` values into the binary.

To ensure cargo re-runs the macro when `plugin.toml` changes, add a one-line
`build.rs` at the crate root:

```rust
// build.rs
fn main() {
    println!("cargo:rerun-if-changed=plugin.toml");
}
```

## C++ plugins

Add the codegen call to your `CMakeLists.txt`:

```cmake
find_package(MalboxPluginSDK REQUIRED)

malbox_generate_runtime_config(
    MANIFEST ${CMAKE_CURRENT_SOURCE_DIR}/plugin.toml
    OUTPUT   ${CMAKE_CURRENT_BINARY_DIR}/generated/malbox_runtime_config.hpp
)

add_executable(my-plugin src/main.cpp ${MALBOX_GENERATED_HEADERS})
target_include_directories(my-plugin PRIVATE ${CMAKE_CURRENT_BINARY_DIR}/generated)
target_link_libraries(my-plugin PRIVATE MalboxPluginSDK::MalboxPluginSDK)
```

In your `main()`:

```cpp
#include <malbox/plugin.hpp>
#include "malbox_runtime_config.hpp"

int main() {
    malbox::PluginMeta meta{/* ... */};
    malbox::run_guest_plugin(
        std::make_unique<MyPlugin>(),
        meta,
        malbox::generated::runtime_config);
    return 0;
}
```

## Install the Plugin to the Registry

Place the built plugin binary and its `plugin.toml` into your configured
plugins directory (the daemon scans this directory at startup and on
filesystem changes). The daemon reads `[runtime].port` from the manifest to
know where to connect, and validates the `[runtime]` section - plugins with
invalid values are marked `Invalid` in the registry and skipped.

## Migrating from env-var configuration

Earlier versions of the SDK read runtime settings from environment variables
(`MALBOX_WORK_DIR`, `MALBOX_PLUGIN_PORT`, `MALBOX_LOG_OVERFLOW_DIR`,
`MALBOX_STASH_THRESHOLD`, `MALBOX_STASH_TTL`, `MALBOX_LOG`). These reads have
been removed. If you have deployment scripts that `set` any of these, delete
those lines - they have no effect and only clutter the launch environment.

## Migrating from `work_dir` to split paths

The single `work_dir` and `log_overflow_dir` fields have been replaced by four
purpose-specific paths under `[runtime.paths]`: `sample_dir`, `artifact_dir`,
`stash_dir`, and `log_dir`. Similarly, `stash_threshold_bytes` and
`stash_ttl_secs` have moved to `[runtime.stash]`, and `state`/`execution` have
moved from `[plugin]` to `[runtime]`.

If your existing `plugin.toml` uses `work_dir`, update it to use the new
`[runtime.paths]` sub-table. Each path has its own platform-aware default, so
in most cases you can simply remove the old fields and rely on the defaults.

**Breaking changes in this release:**

- `state` and `execution` moved from `[plugin]` to `[runtime]`.
- `work_dir` and `log_overflow_dir` were replaced by `[runtime.paths]` with
  four separate fields: `sample_dir`, `artifact_dir`, `stash_dir`, `log_dir`.
- `stash_threshold_bytes` and `stash_ttl_secs` moved to `[runtime.stash]` as
  `threshold_bytes` and `ttl_secs`.
- The Rust `#[malbox(state = "...", execution = "...")]` attribute was removed.
  State and execution are now read from `plugin.toml` only.
- The C++ `RuntimeConfig` struct fields changed from `work_dir`/`log_overflow_dir`
  to `sample_dir`/`artifact_dir`/`stash_dir`/`log_dir`.
- The C++ FFI entry point `malbox_run_guest_plugin` gained a third parameter
  (`MalboxGuestRuntimeConfig config`). The two-argument form is gone.
- The C++ API `malbox::run_guest_plugin(plugin, meta)` gained a third
  argument `const RuntimeConfig& config`. The two-argument form is gone.
- The Rust SDK's `GuestPluginRuntime::new` constructor was removed; use
  `GuestPluginRuntime::with_config(plugin, config)`. Plugins using the
  `#[guest_plugin]` macro are unaffected - the macro handles this for you.
- `malbox_plugin_sdk::internal::init_tracing` now takes a
  `filter: &str` argument.
