---
title: "Event hooks"
description: "How host plugins react to system events through hooks"
---

Besides running jobs, host plugins can react to system events, such as a task completing or the daemon shutting down. Event hooks are notifications only: they are not tied to a job, carry at most one identifier, and cannot push results.

## How event hooks work

The daemon broadcasts system-wide events on a shared channel (`malbox/events/daemon`) that every host plugin listens to. Each plugin also publishes its own lifecycle events (`PluginStarted`, `PluginStopped`) on its per-plugin channel (`malbox/events/plugin/{id}`).

The runtime uses a WaitSet-based reactor pattern. Your plugin sleeps until an event arrives, then routes it to the matching `#[malbox::on_event(...)]` handler, or to a catch-all `on_event` method if no specific handler exists. No manifest configuration is needed.

## Event categories

Events are grouped into four categories based on what triggers them:

| Category | Description |
|----------|-------------|
| **Task events** | Fired during task lifecycle stages |
| **Plugin events** | Fired when plugin processes start or stop |
| **Sample events** | Fired when samples are received or finish processing |
| **System events** | Fired for system-wide occurrences like shutdown or configuration changes |

## Handling events

In your plugin code, use `#[malbox::on_event(...)]` handlers inside `#[malbox::handlers]` to react to specific event variants:

```rust
#[malbox::handlers]
impl MyPlugin {
    #[malbox::on_event(TaskCompleted)]
    fn on_task_done(&self) -> Result<()> {
        info!("A task completed");
        Ok(())
    }
}
```

<Note>
Event hooks are only available to host plugins. Guest plugins do not receive events.
</Note>

## Passing data between plugins

Events do not carry plugin results. To build on another plugin's output, use the orchestrator instead:

- Put your plugin in a later [stage](/task-management/orchestration#stages) with [`[routing]`](/reference/configuration/plugins#routing), so it runs after the plugins it depends on.
- Read task-wide data that earlier plugins wrote with `shared_put`, and re-run automatically when a key changes with `monitored_keys`. See [Shared data between plugins](/task-management/orchestration#shared-data-between-plugins).
- Read indicators from earlier reports with `uses_indicators = true`.
- Receive files that other plugins extracted as their own jobs: a plugin that pushes an artifact with `push_artifact` makes it a child that is routed to every matching plugin.
