## Overview

The Malbox scheduler is the orchestrator inside the daemon. It plans jobs for each artifact of a task, releases them stage by stage, runs them on host plugins and machines, and records the results. For the analysis model it implements (tasks, artifacts, jobs, stages, and limits), see [Orchestration](/task-management/orchestration).

All scheduling state lives in PostgreSQL: tasks, artifacts, the edges between them, jobs, and the result cache. The in-memory components below can be rebuilt from the database at any time.

## Architecture

The orchestrator is built on Tokio and has four kinds of components.

### Coordinator

The coordinator receives new submissions and control commands (cancel, rescan, priority changes) from the HTTP API, and routes them to the right task actor. On startup it:

1. purges expired result-cache entries (and does so again every hour);
2. returns jobs that were running when the daemon stopped to the queue, or fails them if they have no attempts left;
3. starts an actor for every task that is still `pending` or `running`.

### Task actors

Each active task has its own actor. The actor is the only component that changes the task's artifact states and task status. It:

- plans jobs for each new analysed artifact, using plugin [routing](/reference/configuration/plugins#routing) and the [detonation profiles](/reference/configuration/orchestration#detonation-profiles);
- releases each artifact's jobs one stage at a time, replaying cached results when possible;
- admits or drops the child artifacts that finished jobs produced, applying the task's limits;
- decides which child artifacts use the detonation budget;
- enforces task and artifact deadlines, and reloads its state from the database if nothing happens for `stall_check_secs`;
- finalizes the task, its counts, and its verdict when no job is left.

An actor exits when its task finishes. A later rescan of that task starts a new actor.

### Executors

Two executors pick up released jobs:

- The **host executor** claims ready host jobs in priority order, up to `host_concurrency` at once. Each host plugin runs one job at a time, and a task with `max_running_jobs_per_task` running jobs waits for one to finish.
- The **detonation executor** scans ready detonation jobs, acquires a matching machine for each, and runs the session. At most `max_concurrent_vm_boots` machines boot at once. A job stays queued while every matching machine is busy.

Each finished job is ingested: reports are stored, shared data is merged, and every other output becomes a child artifact. The executor then notifies the task's actor.

### Cancellation

Every running job has a cancellation token. Canceling a task, an artifact, or a job cancels its queued jobs in the database and signals the tokens of its running jobs. A canceled host plugin process is killed and, if it is persistent, restarted. A canceled detonation stops its guest plugins and releases the machine.

On daemon shutdown, the coordinator cancels every running job and waits up to 20 seconds for the executors. Interrupted jobs run again on the next start.
